## Implemented evidence

- `contracts/openapi/kelimio-api.yaml` keeps Type-A/Type-B/Type-C attempt payloads answer-key-free and accepts no client-owned score, energy, entitlement, user identity, language policy, or match result. Type B and C require exactly one literal `---`, including overlapping-marker rejection; Type C has no options, and answer submission requires exactly one option ID or typed answer. Under ADR-000/ADR-008, only transaction-specific post-commit feedback reveals the submitted A/B question's correct option or the C question's primary correct-answer text. The answer body has an explicit 8192-byte cap and no-store `413` response, while ownership-scoped reconciliation reveals only the authenticated user's committed result. The profile contract exposes provisional/completed state and accepts a one-time setup command without treating it as legal consent.
- The generation script produces checked-in Dart/Dio and TypeScript clients with a pinned OpenAPI Generator; schema tests cover course, profile, A/B/C question responses and requests, required properties, closed objects, canonical language tags, exact B/C marker structure, mutually exclusive answer/feedback forms, typed-answer body limits, and rejected client-asserted identity or answer-key fields.
- The Kotlin/Spring API has Flyway schema, fail-closed Type-A/Type-B/Type-C storage-to-API mapping, real JWT validation, sanitized provisional identity claims, a server-enforced provisional-profile gate, one-time idempotent profile setup with append-only audit/outbox facts, catalog/enrollment/attempt endpoints, persistent idempotency, authoritative scoring and free-course energy rules, release-pinned manifests, cross-checked append-only facts, transactional outbox transport writes, and a retrying idempotent learner-course progress projection that can be rebuilt from PostgreSQL facts. Type C uses pinned-locale canonicalization inside the transaction, salted replay evidence without retaining learner text, a pre-Jackson body cap using Spring path semantics, early raw-envelope rejection, no-store responses, and owner-scoped lost-response reconciliation.
- A separately gated local-development command creates immutable, provenance-recorded starter release v3 from the supported reviewed-workbook subset using English as its support language. It contains five Type-A, one Type-B, and the exact reviewed-workbook Type-C row; requires authentication; is idempotent; cannot run outside `local`; and creates no user, learning result, entitlement, or production fallback.
- The isolated Excel-preview core snapshots and preflights XLSX packages before read-only SAX parsing, rejects formulas, hidden/active/external content and bounded-resource violations, normalizes the reviewed multilingual workbook grammar without translation fallbacks, deterministically allocates tests, and emits separate allocation and complete-preview SHA-256 digests. Its exact owner-supplied workbook fixture and malicious-package/property tests are checked in; no API, persistence, or release side effect is attached to this core.
- The Flutter client uses the generated API client, AppAuth, secure token storage, Riverpod, `go_router`, Dio, Drift recovery state, generation-guarded and serialized token persistence, private-state purge on session changes (including user-scoped progress), distinct authentication/authorization failures, first-login profile/language/time-zone setup, Turkish/English/Arabic localization, RTL-aware UI, an accessible first-strong-character-directed Type-B inline blank, and privacy-safe Type-C entry with backend-only grading. Drift and diagnostics never retain raw typed answers; typed `413`/`422` validation returns to a blank field with the same reserved submission ID, and ambiguous/lost responses reconcile through the owner-scoped result endpoint. The app also has an explicitly local-only starter-course control, preferred support-language defaults, and bounded/backed-off projected-progress refresh that becomes a retryable error instead of an endless spinner.
- The repository-managed Android API 36 emulator cold-boots without Google Play, maps the local API/OIDC ports through ADB, and has exercised secure storage, the Drift recovery database, session restoration, and signed-out startup on a real Android runtime.
- The internal admin deployment always returns not found until server-side OIDC, MFA, RBAC, and audit exist. The separate public deployment keeps legal/support routes unpublished unless approved server-only content and versions are supplied.
- Local Compose describes PostgreSQL, Redis, Keycloak, an idempotent existing-volume realm reconciler, LocalStack, Mailpit, ClamAV, OpenTelemetry, and an optional API container. Terraform validates an encrypted state bootstrap plus account-guarded development networking/foundation resources.
- Docker Compose has started every local dependency and the API successfully; PostgreSQL V6 is current, the V3-to-V4, V4-to-V5, and V5-to-V6 migration paths preserve legacy answer facts, digest-pinned Testcontainers PostgreSQL transactions run without skips, and existing-volume Keycloak email/SMTP reconciliation, API readiness, OIDC discovery, email capture, LocalStack health, and OpenTelemetry metrics have been exercised locally.
- A guarded one-command Android acceptance runner creates a separate Compose project with random ports and volumes plus a separate `com.kelimio.app.e2e` Android package, performs public Keycloak registration and Mailpit verification before S256 PKCE code exchange, drives the production mobile data/UI path through five Type-A, one Type-B, and one Type-C answer plus sign-out, verifies Type-B replay plus Type-C replay and reconciliation, reaches 7/7 with 420/420 projected score at version 8, and proves cleanup reaches zero project containers, volumes, and networks while normal Compose container identities and ADB reverse mappings remain unchanged.
- GitHub workflows cover backend, mobile, contracts/generated drift, both web deployments, Terraform, secret scanning, dependency/filesystem scanning, runtime-image scanning, and CycloneDX SBOM retention. They are configured but have not run for this branch because the workflows intentionally trigger on pull requests or pushes to `main`; no pull request has been opened.
