## Implemented evidence

- `contracts/openapi/kelimio-api.yaml` keeps Type-A/Type-B/Type-C/Type-D attempt payloads answer-key-free and accepts no client-owned score, energy, entitlement, user identity, language policy, or correctness result. Type B and C require exactly one literal `---`, including overlapping-marker rejection; Type C has no options; Type D has a required null prompt, no options, and separate independently ordered target/support arrays with no public relationship field. Answer submission requires exactly one option ID, typed answer, or complete matching bijection. Under ADR-000/ADR-008/ADR-009, the only client/API responses that may contain the submitted A/B question's correct option, the C question's primary correct-answer text, or the D question's correct mapping are transaction-specific post-commit or ownership-scoped no-store reconciliation feedback. The answer body has an explicit 8192-byte cap and no-store `413` response. The profile contract exposes provisional/completed state and accepts a one-time setup command without treating it as legal consent.
- The generation script produces checked-in Dart/Dio and TypeScript clients with a pinned OpenAPI Generator; schema tests cover course, profile, A/B/C/D question responses and requests, required properties, closed objects, canonical language tags, exact B/C marker structure, mutually exclusive three-way answer/feedback forms, matching cardinality/shape/privacy, typed-answer body limits, and rejected client-asserted identity or answer-key fields.
- The Kotlin/Spring API has Flyway V10, fail-closed Type-A/Type-B/Type-C/Type-D storage-to-API mapping, real JWT validation, sanitized provisional identity claims, a server-enforced provisional-profile gate, one-time idempotent profile setup with append-only audit/outbox facts, catalog/enrollment/attempt endpoints, persistent idempotency, authoritative scoring and free-course energy rules, release-pinned manifests, cross-checked append-only facts, transactional outbox transport writes, and a retrying idempotent learner-course progress projection that can be rebuilt from PostgreSQL facts. Type C uses pinned-locale canonicalization and salted replay evidence without retaining learner text. Type D locks and pins the enrollment support language, issues independently ordered sides, validates one complete two-to-six-item bijection, and grades all-or-nothing. Its durable answer fact contains no explicit mapping or correct-pair count; it stores a random salt, an HMAC-SHA-256 equality token, the external key version, and required `is_correct`, while authored relationships remain in immutable content tables. The staging/production secret keyring remains outside PostgreSQL, source, logs, events, outbox payloads, problem details, and diagnostics; replay resolves the stored version and compares in constant time, failing closed for missing or invalid configuration. This is resistance to candidate testing after a database-only compromise while the external key remains secret, not anonymity or full-compromise protection. The authoritative correctness fact has unavoidable residual disclosure: `true` identifies the authored mapping, and for exactly two pairs `false` identifies the sole swapped mapping. The only client/API responses that may contain the explicit post-commit mapping are the no-store submission and ownership-scoped reconciliation responses.
- A separately gated local-development command creates immutable, provenance-recorded starter release v4 using English as its support language. It contains five Type-A, one Type-B, the exact reviewed-workbook Type-C row, and one four-pair Type-D question from the unambiguous `EV` group; requires authentication; is idempotent; cannot run outside `local`; uses unrelated UUIDv4 item IDs per created course; and creates no user, learning result, entitlement, or production fallback.
- The isolated XLSX parser/planner remains fail closed and is invoked only by the separately started local/test worker after exact-version object acceptance, malware scanning, and immutable archive verification. Approval remains a standalone immutable fact with no course side effect. A separate API transaction consumes only a valid versioned preview and creates exactly one `DRAFT` course, committed initial `ContentChangeSet`, and complete immutable `DRAFT` release hierarchy; it preserves translations, authored distractors, matching-group provenance, settings, and source coordinates without compiling runtime options or activating anything. The isolated real-service E2E drives the reviewed workbook to `COMMITTED`, a clean-invalid workbook to `VALIDATION_FAILED`, and EICAR content to `MALWARE_REJECTED`; it proves owner isolation, digest and idempotency conflict handling, no-store responses, queue drain, immutable evidence, and zero active/public/enrollment side effects.
- The Flutter client uses the generated API client, AppAuth, secure token storage, Riverpod, `go_router`, Dio, Drift recovery state, generation-guarded and serialized token persistence, private-state purge on session changes (including user-scoped progress), distinct authentication/authorization failures, first-login profile/language/time-zone setup, Turkish/English/Arabic localization, RTL-aware UI, an accessible first-strong-character-directed Type-B inline blank, privacy-safe Type-C entry, and an accessible two-stage Type-D target/support selection path with backend-only grading.
